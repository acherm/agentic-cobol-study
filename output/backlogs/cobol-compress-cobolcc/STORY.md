# STORY -- cobol-compress-cobolcc (COBPACK)

## The Claude-Code replica of COBPACK -- same spec, different agent, a modular 3-file decomposition that the Codex sibling never chose

When two coding agents receive the same specification and produce different architectures, the divergence tells you something about the agents, not the spec. The COBPACK domain -- a columnar packer for fixed-length COBOL record files -- was first built by Codex (GPT-5.4) as a two-file monolith: a 1 493-line main program plus a 528-line schema parser subprogram. Claude Code (claude-opus-4-6), given the same MVP0/MVP1/TRUST specification, independently chose a three-file decomposition along an orthogonal axis: a 1 790-line main orchestrator, a 226-line RLESP codec subprogram, and a 110-line CRC32 subprogram. The Codex sibling separated by concern (main vs. schema). Claude Code separated by algorithm (main vs. compression vs. integrity). Neither agent was told how to decompose the source, and neither saw the other's work.

The specification was deliberately layered. MVP0 defined the CPC v0 binary container: an 8-byte COBPACK magic, uint32 version, uint32 record length, uint64 record count, uint32 field count, then variable-length field descriptors, then columnar payloads. The only codec was NONE -- raw columnar transposition, proving that the toolchain (GnuCOBOL 3.2.0, free-format, CBL_* byte-level I/O) could handle binary serialisation at all. MVP1 added RLESP, a space-run encoder with tag-based framing (0x00 literal, 0x01 space-run, MIN_RUN=4), plus AUTO selection for type-X fields and per-field CODEC= schema overrides. The trust layer requested determinism proofs, randomized round-trip fuzzing, corruption fuzzing, and CRC32 cross-checks, all under a wall-clock budget.

Pure COBOL is the load-bearing choice, and the 3-file decomposition makes it more so. GnuCOBOL has no pointers, no unions, no native little-endian helpers. Writing a self-describing binary container under those constraints requires COMP-5 fields with REDEFINES PIC X(n) to emit bytes in native order, CBL_OPEN_FILE/CBL_READ_FILE/CBL_WRITE_FILE for raw I/O, and FUNCTION ORD/FUNCTION CHAR (1-based) for byte manipulation. The Codex sibling kept all of this in a single compilation unit. Claude Code's decision to factor out RLESP and CRC32 as separate subprograms meant the agent also had to exercise COBOL's LINKAGE SECTION, CALL with BY VALUE parameters, USAGE POINTER, and multi-file cobc compilation. The build command -- `cobc -x -free -o cobpack src/cobpack.cob src/crc32.cob src/rlesp.cob` -- links three independent COBOL modules into a single executable. The metrics reflect this: 46 CALL statements, 4 LINKAGE SECTION declarations, 26 USING clauses across the codebase.

The session was remarkable for its economy. Claude Code received the entire specification -- MVP0, MVP1, and TRUST combined -- in a single 7 285-character prompt. There were no follow-up instructions, no clarifications, no scope changes. The agent produced 2 126 lines of COBOL, 516 lines of Python test code, 323 lines of shell scripting, and a 216-line TRUST.md. The TRUST.md itself documents a descriptor offset-bounds guard bug that was "caught, fixed, and pinned by this fuzz loop" -- evidence that at least one real debug cycle occurred within the agent's autonomous execution.

What was delivered covers the full specification surface. The cobpack binary supports compress, decompress, info, and crc32 subcommands. Round-trip correctness is proved across four canonical datasets (small, empty, spaces, random) with NONE, RLESP, and AUTO codecs. Determinism is checked by compressing twice and comparing bytes, then verified against pinned golden CRC32 values. The randomized round-trip fuzzer generates 180 seeded cases with random schemas, gaps, codec overrides, and four content distributions. The corruption fuzzer applies six mutation operators with 2-second subprocess timeouts. And -- distinctively -- a schema fuzzer feeds adversarial garbage to the --schema flag, covering the input surface that the Codex sibling's fuzz suite does not test.

The CRC32 subprogram is the most concrete cross-agent divergence. The Codex sibling implemented CRC32 in Python only, as a test oracle. Claude Code implemented it in COBOL, as a standalone subprogram with a 256-entry lookup table built lazily on first call, using CBL_XOR for the 4-byte XOR in the inner loop. This is production COBOL code, not test infrastructure, and it gives the Claude Code replica a functional capability -- `cobpack crc32 --in FILE` -- that the Codex sibling does not expose.

The surprising insight from the cross-agent comparison is not that the agents produced different code -- they always do -- but that the architectural divergence was orthogonal. Given identical specifications, one agent saw the natural seam as "main program vs. data parser" and the other saw it as "main program vs. algorithm modules." Both are defensible decompositions. But the COBOL-specific consequence of Claude Code's choice -- exercising CALL/LINKAGE/USING across three compilation units, which pushed the mastery score to 50 distinct constructs across all 10 capability categories -- suggests that the architectural decision was also, perhaps accidentally, a richer test of the language.
