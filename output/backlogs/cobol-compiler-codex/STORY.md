# STORY — `cobol-compiler-codex`

## `minicobc`: the second compiler, measured

`minicobc` is the second COBOL-to-C compiler attempt in the corpus, written by Codex in one 10,535-line COBOL source file (`src/minicobc.cob`). It shares its sibling's ambition — a compiler, written in COBOL, that compiles non-trivial COBOL programs — but adds a second axis the `-cc` run does not pursue: it is measured, every step of the way, against GnuCOBOL. GnuCOBOL is wired in as an oracle (stdout diffs, perft counts, python-chess legality), as a runtime-benchmark baseline, and as the bootstrap compiler for the COBOL source itself. On top of that, Codex compiled the COBOL DOOM port end-to-end and published it as a shareable repo (`agentic-cobol-doom`), then caught one of its own miscompiles through a user-prompted regression test.

## Why a parallel attempt is worth running

Running two compiler attempts in parallel is not duplication — it is the point. The `-cc` sibling runs on Claude Code with a 1M-token window; `-codex` runs on Codex CLI (`gpt-5.4`, versions `0.117.0-alpha.24` / `0.118.0-alpha.2`) with a 258 k ceiling. Same task, same external targets (chess engine, game15tictactoe, DOOM, Flappy Bird), different harness. The comparison surfaces harness-level effects that a single run cannot: where the context budget bites, how verbosely each agent writes per line of output, how each reacts to a user challenge on a suspicious performance number. Same contract, two instrumentations.

## Chronology: 48 SB entries, 11 phases, 13 commits

Across four Codex rollouts (main session `019d3a4c…` 2026-03-29 → 2026-04-03, plus three side sessions on 2026-04-03 for cobol85, doom-debug, and game15 equivalence), the work decomposes into **48 SB entries across 11 phases (A..K) mapped 1:1 onto 13 squash commits** — the cleanest step segmentation in the corpus. Phase A bootstraps the compiler and its three core samples (primes, Collatz, GCD). Phase B adds game15tictactoe compatibility and the GnuCOBOL comparison runner. Phase C adds the optimisation mode (`MINICOBC_OPT=1`: constant folding, constant propagation, dead-store elimination, then loop-condition canonicalisation and width-aware integer selection) and the chess-engine compatibility templates. Phase D re-architects the pipeline into a generic front end — `EVALUATE`, `PERFORM VARYING`, paragraph `PERFORM`, groups, `REDEFINES`, `OCCURS`, indexed references, `CALL USING BY VALUE/REFERENCE/RETURNING`, intrinsic functions — and ships DOOM. Phases E–G graduate `gameN`, Flappy Bird, and then the chess engine (phases 1–4: `BOARD`, `FEN`, `ATTACK`, `MOVEGEN`, `MAKEMOVE/UNMAKEMOVE`, `PERFT`, `EVAL`, `SEARCH`, `TIMEUTIL`, `MOVE2UCI`, top-level `COBOCHESS`) onto the generic pipeline, cross-checked against GnuCOBOL at every phase. Phase H is the miscompile hunt. Phase I adds paired-game and Stockfish-skill tournaments; Phase J adds a real `cutechess-cli` Elo harness plus a NIST COBOL85 starter suite; Phase K closes with an `ELSE IF` chain-closure bug fix. Eleven user commit/push requests (`OP-001`..`OP-011`) pace the 13 commits — user-driven checkpointing rather than agent-initiated snapshots.

## Delivered

The externally-observable artefacts: the `minicobc` binary; 69 COBOL files / 11,680 code lines; ~45 generic-front-end regression inputs under `examples/generic/`; 8 optimisation corpus programs under `examples/opt/`; 39 shell drivers and 13 Python comparison scripts under `scripts/`; compatibility templates under `templates/compat/` for chess, DOOM, pygame, and the `minicob.c` bootstrap template; a benchmark manifest with core, optimisation, and compatibility suites; the compiled DOOM published as the `agentic-cobol-doom` repo; four-phase chess harnesses under `tests/chess/`; the paired-game and Stockfish-skill tournament scripts; and `scripts/run_chess_cutechess_elo.py`, which runs an unadjudicated `cutechess-cli` match and reports an Elo estimate with confidence interval. Every benchmark script writes JSON + Markdown; the README carries an explicit caveat that ratios are "strong local signal, not a settled general claim."

## Validation and the chess miscompile

The defining episode of this project is BL-021. Codex was reporting that `minicobc`-built chess ran **faster** than the GnuCOBOL build — a 0.03x runtime ratio that should have raised an eyebrow. The user prompt `PL-044` ("it's very strange to beat the runtime of GnuCOBOL… are you sure? do you check functional correctness?") was the single redirect that turned the project. The agent wrote a direct `QUIESCE` / `ALPHABETA` equivalence harness that bypassed the top-level `SEARCH` wrapper, reproduced the divergence, and isolated the bug to one statement: `MOVE WPC(F-IX - 1) TO FRIEND-L` inside `EVAL` was being lowered as the scalar expression `FRIEND-L = F-IX - 1` instead of loading the indexed array element. Codex added `examples/generic/move_index_expr.cob` as a regression input, patched the indexed-source lowering, and kept the `MINICOBC_OPT=1`-unsafe-for-chess caveat in the README rather than silently widening the optimiser. This is this project's story — not the `-cc` sibling's — and it is the only BL in the set that scored `Q4=2` on robustness. The 20 % tool-output error rate (1,072 of 5,370 tool outputs) is a direct consequence of this operating mode: every construct added to the generic pipeline gets compiled, run, inspected, and cross-checked against GnuCOBOL.

## Compute and context

Four rollouts, 97 user prompts, 5,370 tool calls, 15,631 turn-events, ~11 h of active collaboration, estimated ~$108 at rack rates. The numbers that matter for harness comparison are different: **peak context 244 k / 258 k = 94.7 %** of the available window, and **30 compactions on the main session alone**. The 258 k ceiling bites hard on a project of this size — the agent spent nonnegligible wall-time pruning and re-priming its working memory just to keep the compiler source and the current harness under review. The `-cc` sibling on a 1 M window took 3 compactions on a comparable scope.

## Why it is impressive

The measured-vs-GnuCOBOL framing is the scientifically useful framing: the rubric records 22 of 26 BLs at `Q2=2` (builds and runs) and 17 of 26 at `Q1=2` (correctness full), and the agent caught its own miscompile instead of shipping the 0.03x ratio. The DOOM artefact is a real shareable deliverable, not a local binary. The 48 SB ↔ 13 commit alignment means the project's history is unusually auditable: every squash commit contains a coherent phase, and the phase boundaries coincide with user-driven checkpoint requests.

## Surprising insights

Two numbers from the harness comparison stand out. **30 compactions on `-codex` vs 3 on the `-cc` sibling** — both running essentially the same project — is the clearest per-project measurement of what the context-window difference costs in practice. And the output density: Codex writes roughly **~201 output tokens per LOC** here, against **~99 tok/LOC** on the Claude-Code sibling — about 2× the verbosity per delivered line. Whether that verbosity is scaffolding, explanation, or re-planning is a further question, but the ratio is consistent with the compaction pressure: the same project costs more tokens and more context reshuffling on the smaller window, and the user-commit-pacing pattern (11 of 56 PL entries are commit/push requests) takes on a second function beyond reproducibility — it gives the harness a clean state to carry into the next compaction.
