# STORY — COBOL-chess (cobochess)

A spec-first chess engine in COBOL — 184 F-### features across 27 phases, the most disciplined backlog in the set.

## A ledger before a line of code

Most of the projects in this collection open with a prompt and a compiler. `COBOL-chess` opens with paperwork. By the time Codex writes its first `PROCEDURE DIVISION`, the repository already carries an `ARCHITECTURE.md` describing a 0x88 mailbox, an undo stack, and an `EXTERNAL`-copybook Zobrist singleton; a `SPECIFICATION.md` pinning down UCI semantics and perft invariants; and a `SPECIFICATION_BACKLOG.md` that grows into **184 `F-###` entries organised into 27 phases**, each phase tagged with a timestamp window and each feature pointing to a source line. The opening user brief is short — "I want to build a chess engine in COBOL (GNUCobol)… assess its Elo rating" — but the agent chose to turn it into a spec-led engineering project rather than a vibe-coded prototype. That discipline is what distinguishes this project from its sibling `chess-cobol-cc`, which tackles the same brief with Claude Code and a more improvisational rhythm.

## Why chess in COBOL is hard, and the idioms that make it possible

The language constraints are exactly those of the Claude-Code sibling: no bitboards that feel natural, no 16-bit packed move integers, no recursion by default in GnuCOBOL. What is different here is the *engineering style*. The backlog does not just list "generate pawn moves"; it names the specific language idioms it will rely on. FEN decoding is built on `UNSTRING … DELIMITED BY SPACE` for the six whitespace-separated fields (F-020, `src/fen.cob:49`). Perft, alpha-beta and quiescence all run as `PROGRAM-ID. … RECURSIVE` subprograms with `LOCAL-STORAGE SECTION` move lists so that each frame owns its own mutable state (F-080/F-081, F-109/F-110). The Zobrist tables live in an `EXTERNAL` copybook (`copybooks/hash.cpy`) so that separately-compiled programs share a singleton rather than re-initialising the LCG on every CALL. Moves are explicit records (`M-FROM`, `M-TO`, `M-PROMO`, `M-FLAGS`, `M-SCORE`) — slower than a packed int, but legible in COBOL, which is the point. The architecture document states the trade-off bluntly: "clarity and explicit state transitions over low-level cleverness".

## Three sessions, two agents, 27 phases

The build opens on **2026-02-09 at 10:42 UTC** with a Codex session on `gpt-5.2` that runs for just over two calendar days, through **2026-02-11**, with 24 user turns and 21 assistant turns. Phases 1–11 — scaffold, board and data model, FEN, attack detection, move generation, make/unmake, perft, baseline eval, initial search, UCI, time utility — all carry the same Feb 9 10:32–10:55 window in the backlog: the skeleton is assembled quickly, and *then* tested. Phase 12 lays down `tests/perft_cases.json`, `tools/perft_check.py`, the UCI smoke script, and the `cutechess-cli` + Elo-calculator harness. The next day reveals the first hard bug: the UCI input buffer is `PIC X(512)`, long `position … moves …` strings get truncated, and the engine forfeits on legal play. Phase 14 widens it to `PIC X(4096)` — a one-line fix (F-170, `src/main.cob:25`) that the backlog records as moving Elo from ~675 to ~1129. From there the arc is classical engine engineering: move ordering + piece-square tables (Phase 15, ~1129 → ~1589), Zobrist + a 1 048 576-entry transposition table (Phase 16), LMR + NMP (Phase 17), aspiration + PVS (Phase 20), LMP + mate-distance pruning (Phase 21), pawn structure / piece placement / king safety evaluation rewrites (Phases 22–24), TT-policy and draw-detection refinements (Phase 26), full `wtime/btime/winc/binc/movestogo` time management (Phase 27), a PGN opening book (Phase 28), and finally macOS build hardening. A second Codex session on `gpt-5.4` runs briefly on **2026-03-19** (11 assistant turns in seven minutes) to author README and ARCHITECTURE documentation. A Claude Code analyst pass on `claude-opus-4-6` opens on the same day for the backlog-extraction and assessment work that produced the artefacts this STORY draws from.

## What actually shipped

The binary is `cobochess`, built from **11 COBOL files and 5 copybooks** (3 854 COBOL lines plus 134 copybook lines, 3 359 non-comment code lines, 70 paragraphs, 30 sections). `src/search.cob` alone is 1 362 lines and holds iterative deepening, negamax alpha-beta, quiescence, move ordering, killer and history tables, TT probe/store, LMR, NMP, PVS, aspiration, LMP, and mate-distance pruning. `src/makemove.cob` (615 lines) threads the incremental Zobrist update through every branch — captures, EP, promotions, castling, double-push — and `src/attack.cob` (164 lines) is the legality oracle that the make/unmake cycle calls to filter pseudo-legal moves. The supporting tooling in `tools/` — `perft_check.py`, `uci_smoke.sh`, `engine_check.py`, `elo_run.py`, `elo_calc.py` — makes the Elo claim reproducible, with historical PGNs and JSON summaries preserved under `results/`. Git history is thin: one commit in `COBOL-chess/.git` (the initial "Initial commit: cobochess — COBOL (GnuCOBOL) UCI chess engine (~1600-1700 Elo)" dated **2026-03-19**), plus eight in the analyst session and zero in the short documentation session, for roughly nine commit-events across the three sessions.

## Validation, and the macOS detour

Correctness lives in perft. `tests/perft_cases.json` carries startpos, Kiwipete, an EP-edge position and a promotion position, each taken to depth 5, and `perft_check.py` regression-checks every move-generator change against expected node counts. The Elo number — ~1600–1700 against calibrated Stockfish skill levels — is measured by `elo_run.py` driving `cutechess-cli` with the PGN opening book, parsed through `elo_calc.py` with a 95 % Wilson confidence interval. The last phase of the engine is not an algorithmic refinement but an infrastructure fight: on macOS arm64, GnuCOBOL's default toolchain invokes a GNU `strip` that corrupts the Mach-O binary and the kernel SIGKILLs it on launch. The final phase ships a Makefile that prepends `/usr/bin` to `PATH`, does ad-hoc `codesign -s - -f`, clears `com.apple.quarantine` xattrs, forces `-target arm64-apple-macosx`, sets `.NOTPARALLEL`, and wraps the build in a five-attempt retry loop guarded by `engine_check.py` (F-320–F-328). It is the least glamorous phase and the one most often skipped by agents that stop at "it compiles".

## Compute, context, and what that cost

Across the three sessions the active collaboration time is **5 h 40 m** (20 404 s) against a wall span of 65 days, distributed by task as 10 170 s on `build`, 4 238 s on `understanding`, 2 394 s on `feature`, 1 102 s on `spec`, 791 s on `test`, 615 s on `bug_fix`, 53 s on `plan`. Tool-call volume reaches 1 990, dominated by Codex's 845 `exec_command` and 829 `write_stdin` invocations plus 190 `apply_patch` edits. The conversation ran for **5 786 turns**, and the cost footprint is \$65.91 across 236 M input tokens, 1.19 M output tokens and 898 k reasoning tokens. The headline context number is the one that best explains why the backlog had to be so rigidly phased: on the main Codex session the 258 400-token `gpt-5.2` window peaked at **240 665 tokens — 93.1 % utilisation — and triggered eight context compactions**, spread over Feb 9 evening through Feb 11 mid-morning. A feature-rich, long-horizon project of this kind sits right at the ceiling of what a single Codex conversation can carry.

## Why this one is impressive, honestly

`cobochess` is not novel research; it is a by-the-book chess engine done thoroughly, in an inhospitable language, under a disciplined workflow. The impressive parts are the discipline itself — specification before architecture before implementation before Elo evaluation before build hardening — and the fact that 184 individually small F-### entries compose into a working UCI engine whose move generator is perft-validated and whose playing strength is measured against a calibrated opponent rather than eyeballed. The honest gaps are real: no `run_n` Elo evidence lives in *this* folder (the cutechess results tree lives in the sibling `chess-cobol-cc`), gameplay correctness is inferred from perft rather than tournament PGN here, evaluation stays classical (no mobility, no SEE, no pawn hash), and one of the Codex user prompts was a bug report about the buffer-truncation forfeit, which counts as real friction. Set beside `chess-cobol-cc`, which shares the brief and the language, the cross-agent comparison is the most interesting takeaway: Codex shapes its workflow around fine-grained features and a formal spec, accrues fewer performance reverts in the process, and pays for that discipline with a context window running at 93 % and eight compactions. Same problem, same language, visibly different engineering style.
