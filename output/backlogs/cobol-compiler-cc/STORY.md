# cobol-compiler-cc — A COBOL compiler, written in COBOL

## The closed loop

A COBOL compiler, written in COBOL, that compiles a 1 400-LOC Doom port and a 3 500-LOC chess engine. The closed loop is the point. `cobolcc.cob` (~11 000 LOC) and its sibling interpreter `cobolint.cob` (~4 500 LOC) are both bootstrapped by GnuCOBOL. Once built, the resulting `cobolcc` binary reads COBOL source written by entirely different agent sessions — a Doom port from `agentic-cobol-doom`, an 11-file UCI chess engine from `agentic-chessengine-cobol-codex`, the Game-of-15 DFS suite from `agentic-cobol-game15tictactoe` — and emits C that `gcc -O2 -lm` links into native binaries. Those binaries then run: Doom renders in a terminal, the chess engine speaks UCI, the DFS enumerations match the GnuCOBOL reference to the last game count. The ambition is bootstrap-capable self-hosting, and the evidence that it works is not on a benchmark chart — it is a terminal that plays chess.

## The domain, and why a subset is the honest ceiling

Full COBOL-85 is hundreds of thousands of lines of work spread across twenty years of GnuCOBOL, plus the 2002 and 2014 revisions. No single-session agent is going to match that. The interesting question is not "can you build GnuCOBOL?" — the answer is obviously no — but "what subset of COBOL is enough to compile the programs other agents write in the same language?". That framing is what makes this project a real experiment rather than a toy.

The hard features sit in specific parts of the standard. `PIC` and `USAGE` clauses encode a whole numeric type lattice (`PIC S9(9) COMP-5` is a signed 32-bit int, `PIC S9(18) COMP-5` is a long long, `PIC S9(9)V9(9)` is fixed-point decimal that has to round correctly on overflow). `OCCURS` with `REDEFINES` on top demands that the same memory be reachable through two different name-shapes at once. `LINKAGE SECTION` with `CALL ... USING BY VALUE / BY REFERENCE / RETURNING` is the interop surface to external C — and it is the only reason a COBOL Doom can exist at all, because the ray-caster calls a C `sqrt` and C terminal primitives. `RECURSIVE` programs force per-call activation records on `WORKING-STORAGE`, which is normally static. Free-format versus fixed-format changes how the lexer treats column 7. The intrinsic library — `FUNCTION MOD`, `FUNCTION ABS`, `FUNCTION SQRT`, `FUNCTION INTEGER-OF-DATE`, `FUNCTION TRIM`, `NUMVAL` — is small in count but each one has specific numeric semantics. The project ended up supporting all of these, and the surface covered (57 distinct constructs across 10 of 10 capability categories, 161 `OCCURS` uses, 21 `REDEFINES`, 45 `COPY`, 23 `RECURSIVE`) is where the effort went.

## Eleven days, three sessions, 230 MB of JSONL

Work ran from 2026-03-29 to 2026-04-10 across three Claude Code sessions on `claude-opus-4-6`. The main session (`625f1b9f`) is the weight of the whole project — 10 199 turn events, a raw JSONL of approximately 230 MB on disk, with two internal compaction summaries in the middle of it. A noop second session exists but is six system events. A short build-flag follow-up (`de76ffeb`, 26 events) handled one sidebar question.

The chronology has three clean phases. Bootstrap (three days) builds `cobolint.cob` as a tree-walking interpreter, passes nine test programs against the GnuCOBOL reference, and times out trying to enumerate the full 255 168-path Game-of-15 tree in 2 h 17 m of CPU. That timeout is what motivates the user's PL-003: "write a compiler instead, reuse the interpreter infrastructure." Feature-growth (days three to six) ships `cobolcc` v1, then adds free-format, COMP-5, and CALL-to-C in a single 1 224-line commit that gets Doom compiling, then drops into a long debugging loop on chess. That loop is driven by eleven near-identical "let's adress remaining errors" user prompts (PL-010 through PL-020) and produces 29 compile-fix-recompile commits. Hardening (days seven to eleven) is RECURSIVE program support, the frame-pointer "Approach E" code-gen that gets alpha-beta working, the runtime self-copy guard, the cross-file CU-GRP struct wrapping, and a cutechess-cli tournament. The character of the final days is intensive — nine bug-report-style prompts clustered near the end, all under pressure from the same live chess engine running twenty full games at two time controls.

## What was delivered, concretely

Two COBOL binaries: `cobolcc` (701 KB) and `cobolint` (138 KB). A test corpus that all compiles via `cobolcc`: nine canonical tests (hello, factorial to 12!, FizzBuzz, Fibonacci, prime sieve, four Game-of-15 subsets), five game15 variants, the 1 363-LOC free-format `doom.cob`, and all eleven files of the 3 854-LOC chess engine (`main.cob`, `board.cob`, `fen.cob`, `attack.cob`, `movegen.cob`, `makemove.cob`, `eval.cob`, `search.cob`, `perft.cob`, `time.cob`, `uci.cob`). A `benchmark.sh` harness (332 LOC) with whitespace-tolerant diff against GnuCOBOL. A full README rewrite documenting compilation status, known limitations (EXTERNAL storage, `PERFORM THRU`, file I/O, `GO TO`, level-88), and the seven manual patches still applied to generated `main.c`. Seventy-four git commits, starting from an empty directory.

## Validation: perft, Doom, and a binutils rabbit hole

Validation is where the project becomes genuinely testable. Chess `perft` is the usual gold standard — it enumerates all move sequences to a given depth, and the totals are known constants. `cobolcc`-built `cobochess` produces `perft(depth 5) = 4 865 609` exactly, matching the published reference. The cutechess-cli tournament (twenty games at 10 s + 0.5 s and 30 s + 1 s) runs end-to-end with every game terminating in checkmate and no crashes — the final score is cobolcc 3 wins, GnuCOBOL 17 wins, and that gap is traced cleanly to a compiler-behaviour issue (EXTERNAL storage treated as static per translation unit, which breaks the transposition table) rather than a chess-logic bug. Doom compiles, links, and renders, though the user reported the keyboard handling and runtime speed were broken and the agent did not fix them before moving on; BL-004 is honestly partial.

The end-stage toolchain debugging is telling. A `cobc -x -O2` invocation hangs on macOS ARM64. The investigation (session `de76ffeb`) builds an optimisation-level-by-strip-variant matrix, and the root cause turns out to be Homebrew's GNU `binutils` putting its `strip` ahead of `/usr/bin/strip` on `PATH` — GnuCOBOL's post-link `strip -x` then corrupts Mach-O ARM64 binaries. The fix is `brew unlink binutils` or a `PATH` reorder, and `test_o2_apple` prints `HELLO` at exit 0. This is the agent contradicting the user's stated hypothesis (not an `-O2` bug, not a `-free` bug, a `strip` bug) based on evidence. A tool-output error rate of 8.7 % (325 errors across 3 740 tool outputs) sounds high in the abstract but is normal for a compile-run-inspect loop where every `cobc` or `gcc` invocation on a half-finished code-gen path is an expected parse error.

## Compute and context: the 1 M Opus variant was necessary

The headline number is peak context utilisation of 978 k out of the 1 M Opus window — 97.8 %. This is one of the most context-pressured sessions in the entire project corpus. Three `isCompactSummary` events appear even on the 1 M variant, which means the compiler's own 11 000 LOC plus the chess engine's 3 854 LOC plus the intermediate state of a long debugging loop simply did not fit even once the window was ten times the default. Active collaboration time is 32 h 30 m. Rack-rate cost sits at roughly $5 185. If this project had been run on a 200 k-window model it would have compacted itself into incoherence long before the RECURSIVE rewrite; the 1 M variant was not a luxury, it was the enabling condition.

## Why this matters, honestly

Self-hosting a compiler is traditionally measured in decades of engineer-years. What lands here is not GnuCOBOL-competitive — the project itself documents the gap (no ANSI-85 conformance run, EXTERNAL storage wrong, `PERFORM THRU` missing, no file I/O, seven manual post-transpilation patches) — but it is a demonstrable closed loop. A compiler written in COBOL, compiled by GnuCOBOL, compiling Doom and a recursive alpha-beta chess engine authored by other agent sessions in the same language. That the project needed the 1 M Opus variant and still compacted three times is, in itself, the interesting methodological finding: the ambition of this task pushes against the largest context window currently available.
